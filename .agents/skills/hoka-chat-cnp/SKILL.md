# 현재 채팅의 변경만 커밋·푸시

현재 채팅의 사용자 요청, 실제 편집 기록과 확인 가능한 기준 diff로 작업 범위를 정한다. Git은 변경의 작성 채팅을 기록하지 않으므로 파일명, 수정 시간, 작업 주제만으로 소유권을 추정하지 않는다.

커밋·푸시 규칙은 [hoka-cnp](../hoka-cnp/SKILL.md)를 읽고 적용한다. 이 스킬은 그 전에 커밋 대상을 분리하는 절차다. 스킬 생성·수정 요청 자체는 커밋·푸시 실행 허가가 아니다. 스테이징만 요청하면 스테이징 후 종료하고, 커밋만 요청하면 푸시하지 않는다.

## 1. 작업 범위와 기준 기록

- 이 채팅에서 변경한 내용, 대상 경로, 직접 관련 OKF 갱신과 수행한 검증을 정리한다. 채팅 요약에서 이어받은 작업도 확인 가능한 기록을 사용한다.
- 편집 전 기록이 있으면 기존 변경과 비교한다. 앞으로 편집할 때는 HEAD, 브랜치, `git status --short`, `git diff --cached --binary`, 관련 파일의 `git diff --binary`와 기존 미추적 파일 내용을 먼저 기록한다. 스냅샷은 저장소 밖에 보관한다.
- 실행 시 위 상태와 `git diff HEAD`, 대상 미추적 파일의 내용을 다시 읽는다. 최초 기록 뒤 생긴 다른 작업의 변경도 제외한다. 기존 기록이 없으면 현재 diff 전체를 이 채팅의 작업으로 간주하지 않는다.
- 소유권이 불명확하면 확실한 범위를 정리하고 해당 부분만 사용자에게 확인한다. 다른 채팅의 변경이 사소하다는 이유로 포함하지 않는다.

## 2. 기존 스테이지 보존

- 스테이지가 비어 있으면 선별 절차로 진행한다.
- 이미 스테이징된 변경이 전부 이 채팅의 허가된 범위임을 확인할 수 있으면 그대로 활용한다.
- 다른 작업 또는 출처 불명의 변경이 스테이징돼 있으면 추가 스테이징과 커밋을 멈추고 충돌 범위를 알린다. 기존 스테이지를 임의로 해제하거나 함께 커밋하지 않는다. 분리 대상이 확인되면 다시 진행한다.
- `git reset`, `git restore --staged`, stash, checkout으로 다른 작업을 치우지 않는다. 공유 인덱스나 파일을 과거 스냅샷으로 통째로 복구하지 않는다.

## 3. 이 채팅의 변경만 스테이징

- hoka-cnp의 의도별 커밋 계획을 먼저 보여준다. 각 묶음에 포함할 경로와 혼합 파일의 선택 범위를 명시한다.
- 파일의 변경 전체가 이 채팅에 속함을 확인한 경우에만 `git add -- <정확한 경로>`를 사용한다. 삭제·이름 변경·미추적 파일도 같은 기준으로 판단한다. `git add -A`, `git add .`, 디렉터리·와일드카드 전체 추가는 사용하지 않는다.
- 같은 파일에 다른 채팅의 변경이 있으면 작업 트리를 수정하지 않고 이 채팅 부분만 패치로 만든다. 현재 인덱스를 기준으로 경로·문맥·행 수를 검증하고 저장소 밖 UTF-8 패치 파일에 저장한다. PowerShell 기본 인코딩에 의존하는 리다이렉션은 피한다.

  ```text
  git apply --cached --check <패치파일>
  git apply --cached <패치파일>
  git diff --cached -- <대상경로>
  git diff -- <대상경로>
  ```

- `git add -p` 없이 비대화형 패치로 분리한다. hoka-cnp를 실행할 때는 이 선별된 스테이지만 대상으로 전달한다. 커밋 묶음 사이에도 미스테이징 변경 전체를 다시 추가하지 않는다.
- 같은 행의 중첩 수정, 바이너리, 다른 작업에 의존하는 변경처럼 안전하게 분리할 수 없는 경우는 자동 포함하지 않고 해당 범위의 확인을 요청한다. 패치 적용 실패를 `--reject`나 작업 트리 덮어쓰기로 우회하지 않는다.
- `okf/log.md` 같은 공유 문서도 이 채팅의 항목만 선별한다. `scripts/okf-sync.mjs` 매핑에 따라 소스와 직접 관련 문서를 같은 커밋에 포함한다.

## 4. 검증과 hoka-cnp 실행

- 각 커밋 직전에 `git diff --cached --name-status`, `git diff --cached`를 계획과 대조한다. 선택하지 않은 변경이 미스테이징 상태로 보존되는지도 확인한다. 비어 있는 스테이지에서 전체 변경 추가로 전환하지 않는다.
- `git diff --cached --check`와 `npm run okf:check`를 실행한다. 기능 검증은 변경에 맞게 수행하되 전체 작업 트리 검사와 선별된 커밋의 검증을 구분해서 보고한다.
- hoka-cnp의 메시지·의도별 분할·훅·원격 브랜치 규칙을 적용한다. 훅이 파일을 바꾸면 diff와 소유권을 재검토하고 필요한 부분만 다시 스테이징한다. 다른 작업까지 포함하는 전체 파일 재추가를 하지 않는다.
- 커밋 전후 HEAD·브랜치·인덱스를 다시 확인한다. 동시 변경을 발견하면 최신 상태에서 범위를 재검토한다. 실패 시 인덱스를 통째로 복원하지 않는다. 커밋 후 실제 커밋 diff도 확인한다. 공유 작업 트리의 읽기·검사는 동시 쓰기를 잠그지 않으므로 완전한 원자적 격리를 보장하지 않는다. 충돌이 반복되면 같은 인덱스의 동시 커밋을 중단하고 별도 워크트리 사용을 제안한다.
- 푸시 전에 upstream과 원격 상태를 확인하고 실제 푸시될 커밋 범위를 검토한다. 다른 채팅의 미푸시 커밋이 포함되거나 원격 기준을 확인할 수 없으면 푸시를 멈추고 알린다. 커밋 선별만으로 브랜치의 기존 커밋까지 분리되는 것은 아니다. 임의의 rebase·cherry-pick·force push로 해결하지 않는다.

## 결과 보고

커밋 해시·메시지와 푸시 결과를 간단히 알린다. 남겨 둔 다른 작업의 변경과 확인이 필요한 범위가 있으면 구분한다. 실행하지 않은 단계나 검증을 완료했다고 기록하지 않는다.
